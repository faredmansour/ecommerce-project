# Authentication providers

## Existing authentication

Email/password login and email-based registration remain supported by the existing `/api/auth` JWT flow. The application had no OAuth/OIDC provider integration before this phase. Google is implemented as a backend authorization-code flow using `google-auth-library`: signed state and nonce, PKCE S256, backend code exchange and ID-token verification (issuer, audience, signature, expiry, verified email, nonce), one-time server-side transaction records, and a 60-second one-time exchange code. Provider tokens and secrets are never returned to the browser or logged.

Google sign-in creates a provider-only customer when the verified email is unused. It does not attach a Google identity to an existing password account by email alone. An existing customer can link Google from Account after authenticating; the backend requires a verified Google email matching the account email and enforces unique provider subject ownership. Link transactions also capture the initiating `authVersion` and atomically compare it while saving the link, so a password reset that invalidates the session prevents a pending link from completing. OAuth state is stored hashed in a short-lived server transaction and is bound to a matching HttpOnly, SameSite cookie before callback processing. A valid cancellation consumes the transaction without exchanging a code. A separate random browser-binding secret is also set in a short-lived HttpOnly cookie; only its hash is stored with the exchange. The exchange record is atomically consumed only when the one-time code, browser binding, and expiry all match. Production uses `SameSite=None; Secure` for credentialed cross-origin exchange requests; local development uses `SameSite=Lax`.

All providers are optional. The Google sign-in option stays visible on the login and registration pages; the backend starts the flow only when its Google credentials are configured and otherwise returns a clear unavailable response. `VITE_GOOGLE_CLIENT_ID` remains public client metadata and must be set for a configured frontend deployment.

## Session and browser notes

The current application returns its own short-lived access JWT and refresh token in the authentication JSON response; the backend stores only a hash of new refresh tokens. The frontend does not persist or use the refresh token, and it does not call the backend logout endpoint. A secure HttpOnly refresh-cookie migration remains pending validation of actual production frontend/API origins and browser cookie behavior. The API client already sends credentials and backend CORS uses an explicit origin allowlist, but deployment origin values are provisioned outside the repository. Do not move refresh tokens into browser storage or implement the cookie migration until those origins and the CSRF/SameSite deployment design are confirmed. The frontend does not persist provider access or ID tokens.

On frontend startup, a stored access token is validated through `/api/auth/me`; cached user JSON is never treated as authoritative. Invalid/expired sessions are cleared. Transient validation failures leave the stored access token available for a later retry, but the application treats the visitor as unauthenticated until the backend validates it.

Google account linking requires a currently authenticated session and an explicit authorization-code flow initiated from the Account page. Matching email alone never causes an automatic link. Public browsing and the guest cart do not use provider credentials; sign-in is prompted at protected checkout and the existing cart merge continues after authentication.

Request logs use a generated `X-Request-ID` for correlation and log only the sanitized route, method, status, and safe error type/code. Query strings and error messages/stacks are not written to application logs; long path segments are redacted. Request bodies are not logged.

## Session revocation and legacy token compatibility

Access JWTs, refresh-token records, and password-reset records include the account's `authVersion`/`sessionVersion`. Protected requests and refresh rotation compare that version with the user's current value in the existing account lookup; no additional database round trip is added. Password reset atomically advances the account version only if it still matches the version captured by the reset token, then revokes all outstanding reset and refresh records for that account. This invalidates already-issued access and refresh tokens and prevents sibling reset links (including legacy plaintext records) or concurrent reset requests from changing the password afterward. Existing access and reset tokens without a version are treated as version `0`; they remain compatible until a successful reset increments the account version, after which they are rejected. Customers must sign in again after a password reset.

The token repository's plaintext lookup fallback applies only to `Token.token` records of type `refresh` and `reset`, including logout revocation through `Token.revoke`. New records store token hashes. Email-verification tokens are stored as hashes on the user document and do not use this fallback; Google state and exchange codes use their separate hashed OAuth records.

The committed pre-hash `Token` schema stored refresh and reset values directly, and no existing-record migration or production inventory is present in this repository. Therefore the plaintext fallback is retained temporarily so still-valid pre-migration reset/refresh links and logout requests can complete. Do not remove it or rewrite existing customer records until operators have confirmed a production inventory/expiry policy and have completed a controlled migration or allowed all legacy tokens to expire. Never log the token value while performing that audit.
