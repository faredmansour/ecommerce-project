# Order, Reservation & Payment State Matrix

Status: Approved initial-release consistency matrix recorded in Workstream A3. This is architecture only; no Order transition, Reservation, COD collection, Inventory ledger, or reconciliation behavior is implemented. Approved policy is documented in [Order & Inventory Decisions](order-inventory-decisions.md); MongoDB transaction and Paymob capture verification remain production gates.

## Quantity notation

`q` is the accepted quantity per sellable line; deltas are Inventory-owned. Inventory Reservation `confirmed` means quantity committed to an accepted Order, not delivered. Payment states below use current online Payment vocabulary where possible; COD collection is a distinct future record, not `Payment.status = captured`. For physical on-hand quantities, goods remain in `onHand` until warehouse dispatch; returned goods re-enter only after receipt and inspection.

For every active Reservation, `initialExpiresAt` is server-owned and 15 minutes after creation, with no automatic extension. If payment is UNKNOWN or still processing at that deadline, the Reservation enters `expiry_pending` and remains reserved for one additional 10-minute resolution grace. New payment execution is blocked during grace. The grace only resolves the existing attempt; it does not authorize a new attempt. At grace expiry, release is idempotent; later capture requires manual review/compensation.

## Coordinated business scenario matrix

| Scenario | Order | Reservation | Payment / collection | Inventory quantities and required handling |
|---|---|---|---|---|
| 1. Draft created | `draft` | none | none | No balance change. Draft is unpayable. |
| 2. Reservation active | `draft` until link completes, then `pending_payment` | `active` | none | `reserved += q`; `available -= q`. If Order link fails, saga retries or releases. |
| 3. Payment created (prepaid) | `pending_payment` | `active` | `created` | No quantity change. Amount/currency from immutable Order snapshot only. |
| 4. Payment execution started | `pending_payment` | `active` | Payment typically `pending` or `requires_action`; attempt `REQUESTING`/`SESSION_CREATED` | No quantity change. Provider call is outside DB transaction. |
| 5. Provider timeout / UNKNOWN | `pending_payment` | `active` for 15 minutes, then `expiry_pending` for a 10-minute resolution grace if unresolved | Payment may remain `pending`/`requires_action`; execution attempt `UNKNOWN` | Keep `reserved` during grace and block new payment execution; do not initiate another attempt. Release idempotently at grace expiry if still unresolved. |
| 6. Verified decline | `pending_payment` while retry policy permits; otherwise `cancelled` | `active` during permitted retry; then `released` | Failed Payment is terminal; a retry uses a new Payment ID/key only after verified no-capture outcome | Retry same checkout only by policy; final failure releases once: `reserved -= q`, `available += q`. |
| 7. Verified capture received | `pending_payment` while coordinator runs | `active` or `expiry_pending` | `captured` only after provider capture semantics are verified | No change until confirm command. Durable saga records capture event and validates Order/amount/currency/reference. |
| 8. Reservation committed | `pending_payment` until Order transition | `confirmed` (terminal hold record) | `captured` | `reserved -= q`, `committed += q`; `available` unchanged. Short-lived saga intermediate; retry Order confirmation. |
| 9. Order confirmed (prepaid) | `confirmed` | `confirmed` | `captured` | Captured evidence and committed allocation must match. No further quantity change. |
| 10. Reservation expired (no unresolved attempt) | `expired` after coordinator records expiry | `expired` | none, `failed`, or `cancelled`; not captured | `reserved -= q`, `available += q`. Atomic expiry transition + ledger/outbox. |
| 11. Customer cancels before dispatch | `cancelled` | `released` if active; confirmed Reservation remains terminal | No payment, failed/cancelled, or captured with compensation tracked | Active hold: `reserved -= q`; committed stock: explicit Inventory cancellation `committed -= q`; if captured, refund/void is separate. |
| 12. Admin/operations cancels | `cancelled` only through authorized command with reason/evidence | Same Inventory compensation as customer cancellation | Financial outcome unchanged by status command; captured amount may require refund | Same as above. Generic admin status assignment cannot directly alter buckets. |
| 13. Late capture after terminal Order | `expired`/`cancelled`; never reopened | `expired`/`released`, or terminal `confirmed` if already allocated | `captured` remains a financial fact | No stock is recreated or committed from a terminal hold. Manual review/approved void-refund or new replacement allocation only. |
| 14. COD confirmation | `confirmed` after policy/eligibility and active Reservation | `confirmed` | No electronic Payment. Future COD collection obligation is `due` at dispatch. | `reserved -= q`, `committed += q`; `available` unchanged. No claim of cash collected. |
| 15. COD collection | Usually `shipped` or delivery-in-progress | `confirmed` terminal Reservation record | CODCollection `collected` for full amount; no electronic capture | No stock change at cash handoff; shipment already removed stock from warehouse. Append audited collection evidence. |
| 16. Shipment / dispatch | `shipped` after verified handoff | `confirmed` | Prepaid `captured`; COD collection `due` or subsequently `collected` | Exactly once per dispatched line: `onHand -= q`, `committed -= q`; `available` unchanged. Inventory dispatch ledger + Fulfillment outbox. |
| 17. Delivery refusal/failure | Remains `shipped` while return path is unresolved; later cancellation/return outcome by policy | Reservation remains terminal `confirmed` | COD remains uncollected; prepaid remains captured unless refund workflow acts | No immediate stock increase while goods are with carrier/customer. On warehouse receipt and inspection, append return and `onHand += accepted q`. |
| 18. Delivery completed | `completed` | Reservation terminal `confirmed` | Prepaid stays `captured`; CODCollection must be `collected` or exception recorded | No stock change; dispatch already decremented onHand/committed. Completion is Fulfillment evidence. |
| 19. Refund issued | Order remains in its lifecycle state (`cancelled`, `completed`, etc.) | No Reservation reopen | Payment refund record/ledger indicates partial/full refund; Payment capture fact retained | No inventory change. A separately received/inspected return may increase onHand; refund alone never does. |
| 20. Return received after delivery | Order lifecycle remains completed/return workflow-linked | Original Reservation terminal | Refund may be pending/completed independently | Accepted returned quantity: `onHand += q`; no reserved/committed delta unless a new order is explicitly allocated. |
| 21. COD delivery refused and goods returned | Cancellation/return disposition recorded by Order/Fulfillment | Original Reservation terminal | CODCollection `not_collected`/failed attempt; no electronic capture | No change while in transit; accepted warehouse return increases `onHand` once. |
| 22. Payment captured but Inventory commit fails | `pending_payment`; not confirmed | Active/expiry-pending, or unavailable/terminal conflict | `captured` | Keep financial fact, retry same commit if eligible; otherwise freeze fulfillment, open urgent reconciliation and compensation case. Never oversell. |
| 23. Checkout orchestration timeout | `pending_payment` while saga resumes; `expired` only after approved expiry path | Existing `active`; at deadline `expiry_pending` if Payment is pending/authorized/unknown, otherwise `expired`/released | Existing Payment/attempt remains; do not create another charge during resume | Recover saga by checkout/idempotency identity. Timeout alone changes no stock or Payment fact. |
| 24. Customer/admin cancellation races with capture | CAS winner determines state: cancellation may set terminal `cancelled`, or capture path confirms first and cancellation becomes separate compensation | If cancellation wins, release active hold/adjust committed pre-dispatch stock; if capture wins, Reservation commit may complete before cancel path evaluates | `captured` is retained if verified even when cancellation wins | State/version CAS and event IDs serialize commands; a later capture after terminal cancellation is compensated, never reopened. |

## Stock lifecycle transition table

All rows operate per sellable/warehouse and use integer quantities. Multi-line reservation and any multi-document Inventory transition require one Mongo transaction. Outbox publication is at least once; consumers dedupe by immutable event/command ID. No provider HTTP call is part of an Inventory transaction.

| Business transition | Quantity delta | Owner | Transaction / precondition | Idempotency | Audit/ledger |
|---|---|---|---|---|---|
| 1. Stock received/initialized | Receipt: `onHand += q`; `available += q` | Inventory receiving/adjustment service | Conditional update and receipt record/ledger in local txn; validated physical receipt and nonnegative integer | Receipt/document line ID unique; replay returns prior result | `receipt` or `initial_stock`, source document, actor, reason, before/after balances |
| 2. Reservation created | `reserved += q`; `available -= q` | InventoryReservationService | Atomic conditional availability predicate; all lines commit or none | Checkout/customer key + request hash; one active hold per checkout | `reservation` event per item/line with Reservation/order/checkout refs |
| 3. Reservation released | `reserved -= q`; `available += q` | InventoryReservationService | Active Reservation only; transaction with terminal state and ledger | Release command ID; exactly once; conflicting terminal state returns conflict | `release` event with failure/cancel reason and actor |
| 4. Reservation expired | `reserved -= q`; `available += q` after expiry or grace | Expiry worker via Inventory service | Due/state/version CAS; unresolved Payment first enters `expiry_pending` with no quantity change | Reservation ID + expiry generation; duplicate workers cannot release twice | `expiration` event; job/run/decision timestamps and resolution evidence |
| 5. Reservation committed | `reserved -= q`; `committed += q`; `available` unchanged | InventoryReservationService, called by trusted prepaid coordinator or approved COD flow | Active or eligible `expiry_pending`; matching Order and required capture/COD acceptance evidence | Capture/acceptance event command ID; cannot commit terminal hold twice | `confirmation`/commitment event with Payment or COD decision reference |
| 6. Order processing begins | No quantity change | Fulfillment service; Inventory remains source for balances | Confirmed Order and committed allocation required; durable Fulfillment accept event | Fulfillment work/task ID | Fulfillment audit; Inventory ledger may record zero-delta reference only if policy requires, not a balance movement |
| 7. Order shipped/dispatch | `onHand -= q`; `committed -= q`; `available` unchanged | Inventory dispatch command, triggered by Fulfillment | Warehouse handoff confirmed; one atomic update of both quantities; q cannot exceed committed | Shipment-line dispatch ID unique | `dispatch` event with shipment, line, carrier handoff, actor/system, before/after |
| 8. Shipment partially fulfilled | **Unsupported initially.** If later approved, decrement `onHand` and `committed` only for dispatched line quantity | Inventory dispatch service | Per-line/quantity dispatch txn; remaining quantity stays committed; Order cannot be fully shipped until all lines dispatched | Unique shipment + line + quantity allocation ID | `partial_dispatch` per line, immutable shipment reference; never replay whole-order decrement |
| 9. Delivery completed | No quantity change; stock already left on dispatch | Fulfillment service | Delivery evidence accepted and all required shipments complete | Delivery event ID | Fulfillment audit; no second Inventory deduction |
| 10. Order cancelled | Before dispatch: active hold `reserved -= q`; committed allocation `committed -= q`. After dispatch: no immediate balance change. | Order cancellation saga invokes Inventory release or committed cancellation; post-dispatch uses returns | State/version and dispatch status checked; no generic status edit | Cancellation command ID plus per-reservation/line compensation IDs | `release` or `commitment_cancelled`; actor/reason/evidence; history/outbox |
| 11. Return received | Accepted inspected quantity: `onHand += q`; `reserved`/`committed` unchanged | Inventory returns service after warehouse receipt/inspection | Physical receipt and disposition recorded; rejected/damaged goods excluded from sellable onHand | Return authorization + received line ID | `return` event with original Order/shipment, condition, quantity, inspector |
| 12. Refund issued | No quantity change | Payments/refunds domain | Provider or finance refund evidence; independent of physical return | Refund idempotency key/provider refund ID | Append-only refund ledger/record; no Inventory ledger event unless a separate physical return occurs |

For every row, failure before local transaction commit leaves all local quantity, state, ledger, and outbox writes unapplied. For cross-domain rows, the owning transaction commits an outbox command and retries downstream effects; do not pretend Order, Fulfillment, Inventory, and Payment are atomically updated together.

`Payment.status` currently has no `refunded` state; refund statuses above refer to a future refund record/ledger contract and are not a proposal to change runtime enum silently. Similarly, `CODCollection` and its courier-settlement status are proposed separate records, not present in current code.

## Invalid or inconsistent combinations

The following are invalid steady states. Some may exist briefly while a durable saga step is retrying; each such intermediate must have a persisted outbox/command, age/SLA, and alert. A missing recovery record turns it into an incident.

| Combination | Why invalid | Recovery |
|---|---|---|
| Order `confirmed` prepaid while Payment is not trusted `captured` | Order claims acceptance condition not met | Keep/return to review only through audited correction; no fulfillment; verify provider evidence. |
| Order `confirmed` while Reservation is not `confirmed`/committed | Order has no allocated inventory | Block fulfillment; retry idempotent Inventory commit if active and eligible, otherwise compensate payment/review. |
| Active Reservation for terminal `cancelled`/`expired` Order | Hold leaks stock and conflicts with terminal Order | Retry release/expiry; alert if terminal Order is stale. |
| Captured Payment + terminal Order + released/expired Reservation, followed by automatic reopening | Violates terminality and may oversell | Preserve facts; manual/approved compensation or a new replacement Order/Reservation. |
| Payment `captured` for COD collection with no electronic tender | Misstates cash as provider capture | Use CODCollection evidence; correct only through auditable Payment operations, never direct state rewrite. |
| Reservation committed more than once or `reserved`/`committed` exceed `onHand` | Violates stock invariant / double allocation | Stop stock writes, reconcile append-only ledger and InventoryItem, append correction only after authorized count. |
| Shipment event decrements `onHand` twice or decrements only `onHand` while leaving committed | Double deduction or stale commitment | Deduplicate by shipment-line event ID; atomic dispatch updates both quantities. |
| Order `shipped` with no accepted dispatch event | Order and physical stock disagree | Hold Order projection; reconcile carrier and Inventory dispatch evidence. |
| Order `completed` without delivery evidence | Fulfillment completion is unproven | Reconcile delivery evidence; no admin arbitrary assignment. |
| Refund changes `onHand` without a physical inspected return | Refund is financial, not physical stock receipt | Reverse only through audited Inventory correction if an actual count proves discrepancy. |
| CODCollection marked collected before authorized handoff/receipt | Cash evidence is unsupported | Investigate operator evidence and append correction; do not infer from Order status. |

## Reconciliation scope

Future cross-domain reconciliation should join Order, Reservation, Payment/refund or CODCollection, Fulfillment shipment events, and Inventory ledger by immutable IDs. It must classify inconsistencies and create an auditable case. It is read-only by default; repairs use explicit idempotent commands owned by the relevant domain. The existing `PaymentReconciliationService` does not read Reservations, CODCollection, Fulfillment, or Inventory ledger and does not repair state.
