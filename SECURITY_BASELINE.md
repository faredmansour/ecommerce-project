# Security Baseline — Phase 2

This document records the Phase 2 security baseline and intentionally deferred risks. It is a focused verification reference aligned where applicable with OWASP ASVS 5.0.0; it is not an ASVS certification or a complete control assessment.

## Implemented in this phase

- Public registration no longer accepts a privileged role. Unknown `role` input is stripped by Joi, and the controller explicitly creates a `user` account.
- Protected requests load the current user role from MongoDB, so a stale JWT role claim cannot grant an admin route. Missing users are rejected.
- Admin-only product/category/order/upload routes retain server-side authentication and role checks. Cart, wishlist, addresses, coupons, orders, and reviews remain scoped to the authenticated user where applicable.
- Upload routes require admin authentication, have an upload-specific per-process rate limit, accept only JPEG/PNG/WebP declarations and matching file signatures, cap files at 5 MB, and limit multipart counts. Storage filenames are generated by the server; original paths/extensions are not used. Product image upload remains optional.
- Refresh/reset tokens issued by the current code are stored as SHA-256 digests. Existing plaintext token records are temporarily accepted for rotation/revocation compatibility.
- Product listing validates scalar query values, validates category IDs, escapes search strings as literal text, bounds search length and pagination, and caps `limit` at 1000 to preserve the admin's existing request.
- Resource-ID routes validate ObjectId syntax before database lookup. Order shipping fields are validated against the existing address requirements.
- Production 500 responses from the shared error handler and caught controller failures return generic messages; detailed errors are written to server logs. Development keeps diagnostic details.
- Security regressions cover public role escalation, stale role claims, owner/admin order access, malformed product IDs/search/pagination, upload authorization/content/size/filename/rate limits, and production error redaction.

## Authorization boundary review

- Anonymous requests: cart and protected resources require a bearer token; upload requires both authentication and admin role.
- Customer-to-admin: product/category mutation, admin dashboard, order status updates, and upload are server-side admin-gated.
- Ownership: cart and wishlist are loaded by user; address mutations filter by both address ID and user; order detail checks owner or current admin role.
- Public resources: product/category/review reads remain public by design. Review writes require authentication and a unique user/product index.
- Public account creation always creates a customer. There is no in-app privileged account provisioning route; trusted admins must be provisioned outside public registration.
- The public registration UI and API helper no longer offer/send a role field.
- Product, category, cart-item, order-item, wishlist product, order, cart, address, and review resource identifiers are shape-validated as Mongo ObjectIds where those routes use Mongo IDs.
- A server-side product search is treated as literal text, and query pagination/search inputs have scalar/length bounds.
- Startup rejects an absent, under-32-character, or obvious `change-me` JWT secret.
- The OpenAPI upload route now documents bearer authentication and admin authorization.

## Deferred risks — not fixed in Phase 2

### Checkout, payment, and inventory

- Order creation still trusts client-supplied items, item prices, and `totalAmount`; it does not reload catalog prices or verify stock.
- Stripe PaymentIntent amount and currency still come from the client (USD default), and the intent is not bound to a server-created order.
- There is no persisted payment entity/state, provider verification, signed webhook, idempotency, refund flow, or asynchronous payment confirmation. Redirect/client state must not be trusted as payment success.
- Stock is stored on the product but is not decremented, reserved, released, or updated atomically. Overselling and payment/order/cart partial failures remain possible.
- Coupon minimum/discount application is not authoritatively recalculated in the order controller; coupon usage limits are absent.

These are intentionally deferred to the pricing, inventory, order-lifecycle, and provider-agnostic payment phases. Do not treat the current COD/Stripe checkout as production-ready.

### Sessions and existing records

- The frontend still stores access tokens in `localStorage`. Moving to `HttpOnly`, `Secure`, `SameSite` cookies requires a coordinated session/CSRF/CORS migration and is deferred.
- Existing plaintext refresh/reset token records are not bulk-migrated. They can be used once through the compatibility path and are hashed when newly issued; expired/revoked legacy records may remain stored. Plan a controlled token migration or revocation before production rollout.
- Accounts created with `role: "admin"` before the registration fix remain admins in MongoDB. Audit and demote any untrusted accounts as an operational rollout step; this phase does not mutate live user data.
- Password reset tokens are still delivered in a query-string URL. Use a future session/security review to assess referrer/history exposure and token lifecycle cleanup.

### Uploads, operations, and platform

- Image signature checks validate format markers, not full decoding or image dimensions. Decompression/resource-exhaustion risks require a later safe image-decoding/normalization decision.
- Upload throttling uses the default in-memory limiter store and is per process/IP; it is not a distributed quota. Local uploads are public static files and depend on deployment storage/permissions.
- Image signature checks are not a full decoder, so polyglot payloads and decompression/resource exhaustion remain. Existing static upload hosting also needs deployment-level execute/content handling review.
- Rate-limit client IP behavior behind Render/reverse proxies depends on configuring Express `trust proxy` narrowly; that platform-specific configuration is not changed here.
- Refresh/reset token records have no TTL index, so expired/revoked records can accumulate.
- `seed.js` deletes all products and categories before re-seeding, catches errors without setting a failing process exit code, and must not be used against production data.
- `/health` is liveness-only and returns HTTP 200 while reporting the MongoDB state; it is not a readiness gate. Deployment configuration still needs a separate DevOps correction phase.

## Verification

- Backend tests: 7 suites and 40 tests passed after Phase 2 hardening, including registration/RBAC, stale role claim, refresh/reset token hashing and replay, upload controls, product query limits, ID validation, order ownership, and error redaction.
- Frontend build and lint are not security certification. Existing frontend lint warnings are tracked separately.
- No payment provider, payment lifecycle, inventory reservation, catalog redesign, UI redesign, CI change, or production data migration was implemented here.
